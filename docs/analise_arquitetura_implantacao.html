01 — Contexto

De onde viemos e para onde vamos?

Entender o modelo atual e essencial para avaliar o impacto de cada alternativa.

Modelo Atual (Legado)
  • Instalado fisicamente em cada cliente
  • Banco SQL Server proprio por cliente (servidor do cliente)
  • Licenca por usuario — faturamento por cliente
  • Atualizacoes: visita manual ou acesso remoto cliente a cliente
  • WinForms — executavel instalado nas maquinas
Objetivo (ERP Web)
  • Acesso via browser — zero instalacao nas maquinas
  • Backend .NET 10 + API REST
  • Banco SQL Server 2008 legado
  • Atualizacoes centralizadas (idealmente)

O problema centralAlguns clientes possuem bancos de dados muito grandes e servidores dedicados. Isso impede uma solucao unica de hospedagem centralizada sem uma analise cuidadosa de isolamento, performance e custo por cliente.
02 — Suas Duvidas Respondidas

As 4 questoes em analise

Pergunta 1
Onde ficara a aplicacao e o banco de dados?
Existem tres modelos possiveis de hospedagem, e a escolha depende do perfil de cada cliente:

A) On-Premises do Cliente (manter o modelo atual)
O servidor .NET e o banco SQL Server ficam na infraestrutura do proprio cliente. A diferenca do legado e apenas que o frontend passa a ser acessado via browser em vez de executavel. Para clientes com bancos grandes e servidores dedicados, este e o modelo de menor risco no curto prazo.

B) Cloud dedicada por cliente (VM isolada)
Cada cliente ganha uma maquina virtual na nuvem (Azure, AWS) com sua propria instancia da API e seu proprio banco SQL Server. Permite atualizacoes centralizadas mas mantem isolamento total de dados.

C) SaaS Multitenant (unica instalacao, todos os clientes)
Uma unica aplicacao e infraestrutura atendem todos os clientes. Os dados sao separados por schema ou por banco dentro do mesmo servidor. Modelo mais eficiente em custo de operacao, mas o mais complexo para migrar.
Pergunta 2
Sera uma unica instalacao para todos os clientes?
Nao necessariamente — e misturar os modelos e valido.

Voce pode ter uma estrategia hibrida:
- Clientes pequenos: SaaS compartilhado (custo baixo)
- Clientes medios: instancia cloud dedicada por cliente
- Clientes grandes (bancos volumosos): on-premises no servidor do cliente

Isso e exatamente o que ERPs como SAP Business One, Protheus e Senior fazem: oferecem o mesmo produto em multiplos modelos de implantacao, deixando o cliente escolher com base em porte e investimento.
Pergunta 3
Em instalacoes isoladas, como controlar as atualizacoes?
Para instancias em cloud (Azure / AWS): Voce implanta a nova versao em um pipeline CI/CD (GitHub Actions, Azure DevOps) que atualiza todas as VMs automaticamente. Uma tag de versao pode controlar quais clientes recebem a atualizacao primeiro (canary release).

Para on-premises no cliente: A API .NET pode ser empacotada como um container Docker. A atualizacao vira um simples "docker pull + docker-compose up" que o cliente executa ou que voce executa remotamente via acesso autorizado. Muito mais rapido que instalar um executavel em cada maquina.

Controle de versao por cliente: Um painel interno (backoffice) pode registrar a versao instalada em cada cliente, quando foi a ultima atualizacao, e permitir disparar atualizacoes remotas de forma controlada.
Pergunta 4
E possivel transformar em SaaS? Qual o custo e impacto?
Sim, e possivel — mas e uma transformacao profunda e de medio/longo prazo.

O SaaS exige que a aplicacao seja multitenant: um unico sistema atende multiplos clientes simultaneamente com dados completamente isolados. O .NET 10 + EF Core suportam isso nativamente com as estrategias certas de banco. Os impactos sao detalhados na secao seguinte.

05 — SaaS em detalhe

O que e necessario para virar SaaS?

Transformar um ERP legado em SaaS multitenant e um projeto de medio/longo prazo. Estes sao os principais pilares.

DB

Banco Multitenant

Todas as tabelas precisam de TenantId. Dados de clientes diferentes coexistem no mesmo SQL Server com isolamento por schema. Impacto: muito alto no banco legado.

API

Middleware de Tenant

A API .NET precisa identificar qual cliente esta fazendo a requisicao e injetar o contexto do tenant em todo o pipeline. Requer refatoracao do DbContext.

ID

Autenticacao Centralizada

Um sistema de Identity unico (Keycloak, Azure Entra ID B2C) gerencia usuarios de todos os clientes com isolamento por tenant.

$

Billing e Assinatura

Integracao com plataforma de cobranca recorrente (Stripe, Asaas). Controle de planos, usuarios ativos, funcionalidades habilitadas por assinatura.

LOG

Monitoramento Multitenant

Logs, alertas e dashboards precisam distinguir eventos por tenant. Application Insights ou Grafana com tags de tenant em cada evento.

URL

Dominios e Subdomnios

Cada cliente pode ter seu subdominio: clienteA.versatus.com.br. O load balancer roteia para a instancia correta identificando o tenant pelo subdominio.

!
Alerta critico: bancos de dados legadosO SQL Server 2008 nao possui suporte nativo eficiente para multitenancy com Row-Level Security (RLS foi introduzido no SQL Server 2016). Transformar clientes com SQL Server 2008 em SaaS exigiria uma migracao de banco como pre-requisito — um projeto dentro do projeto.
Nossa recomendacao tecnica

Comece com Cloud Isolada por Cliente. Construa o caminho para SaaS gradualmente.

O Modelo B (VM cloud dedicada por cliente) e o equilibrio ideal entre modernizacao imediata e risco controlado. Ele resolve o maior problema do legado (atualizacoes manuais cliente a cliente) via CI/CD, mantem isolamento total de dados, acomoda clientes com bancos grandes com VMs de maior capacidade, e permite migrar para SaaS no futuro de forma gradual — comecando pelos clientes menores e novos.

Para clientes que exigem dados em sua propria infraestrutura, o Modelo A (on-premises + app web) continua sendo viavel e compativel com a mesma codebase — a API .NET e o frontend React/Blazor rodam igualmente em cloud ou on-premises.

06 — Roadmap Sugerido

Plano de evolucao da arquitetura

Fase 1
0-6 meses

Migracao Web com On-Premises

Entregar o ERP web funcionando na infraestrutura atual de cada cliente. O cliente usa o browser mas o servidor ainda e dele. Validar as telas migradas em producao real com clientes piloto.

Fase 2
6-12 meses

Cloud Isolada para clientes novos e pequenos

Novos contratos ja nascem em VMs na cloud (Azure/AWS). Configurar pipeline CI/CD para deploy automatico. Implantar painel de controle interno de versoes por cliente.

Fase 3
12-24 meses

Migracao de clientes legados para cloud

Migrar progressivamente os clientes do modelo on-premises para VMs em cloud, comecando pelos menores. Oferecer beneficios (backup automatico, menor custo de suporte) como incentivo.

Fase 4
24+ meses

SaaS Multitenant (opcional, para segmento SMB)

Criar uma versao SaaS do produto para clientes pequenos e novos que nao exigem isolamento total. Planos de assinatura mensal. Clientes corporativos continuam em instancias isoladas. Dois produtos, um codebase base compartilhado.
