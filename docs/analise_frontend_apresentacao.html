01 — Contexto

O que estamos decidindo?

O sistema ERP Versatus está sendo migrado de um cliente desktop (WinForms + C#) para uma plataforma web moderna. O backend já foi definido — .NET 10 com API REST. A decisão em aberto é: qual tecnologia usaremos no frontend?

Restrições do ambiente:
Backend definido em .NET 10 · Banco SQL Server 2008 legado · Time com background predominante em C# · Objetivo: acesso via browser (zero-install) · Produto ERP corporativo (não SaaS público)
ℹ️
Sobre a stack atual O projeto já tem código produzido em React 19 + TypeScript + MUI v9: infraestrutura CRUD OOP, formulários de Entidade e Condição de Pagamento, sistema de menu dinâmico com favoritos, autenticação e layout completo. Qualquer migração agora implica descartar esse trabalho.
02 — Alternativas Avaliadas

As tecnologias sob análise

Avaliamos seis tecnologias considerando o contexto do projeto: time C#, ERP corporativo, acesso via browser.

⚛️

React 19Stack atual

Meta · TypeScript · MUI v9
    Prós
  • Ecossistema mais rico do mercado
  • Maior pool de vagas/freelancers
  • Performance de renderização excelente
  • Biblioteca de componentes premium (MUI)
  • Debugging avançado (DevTools)
  • Suporte PWA e offline
    Contras
  • Exige JavaScript/TypeScript
  • Curva alta para time 100% C#
  • Ecossistema separado do .NET
  • Sem compartilhamento de modelos
Veredicto: Melhor opção técnica de mercado, porém exige fluência em TypeScript que o time atual não possui.
🔷

Blazor WebAssemblyRecomendado p/ C#

Microsoft · C# · MudBlazor / Radzen
    Prós
  • Time escreve C# puro
  • Compartilha DTOs e validações com o backend
  • IntelliSense e tooling do Visual Studio
  • Fortemente tipado sem configuração extra
  • Suporte offline (PWA)
  • Ecossistema Microsoft (Azure, Entra ID)
    Contras
  • Bundle inicial de 5–15 MB
  • Performance inferior ao React em listas grandes
  • Ecossistema de componentes menor
  • Debugging no browser mais limitado
  • Menos vagas no mercado
Veredicto: Estrategicamente a melhor opção para times 100% C#. Bundle size é o principal trade-off — aceitável em redes corporativas.
🔌

Blazor ServerNão recomendado

Microsoft · C# · SignalR
    Prós
  • Zero bundle size no browser
  • C# puro no servidor
  • Acesso direto ao EF Core
    Contras
  • Requer conexão WebSocket permanente
  • Latência por clique (roundtrip ao servidor)
  • UI congela se a rede cair
  • Escalabilidade cara (RAM por sessão)
  • Não funciona offline
Veredicto: ❌ Inviável para ERP. A latência por clique em formulários complexos e a dependência de conexão permanente são críticos.
📱

.NET MAUIFora do escopo

Microsoft · C# + XAML · Windows/iOS/Android
    Prós
  • Performance nativa (sem browser)
  • C# e XAML — familiar para WinForms
  • Acesso a hardware (impressora, câmera)
  • Multiplataforma: Windows, iOS, Android
    Contras
  • NÃO É WEB — requer instalação
  • Distribuição de atualizações por pacote
  • Não roda em browser
  • Ainda imaturo em 2025 (bugs conhecidos)
Veredicto: ❌ Fora do objetivo. O projeto precisa de acesso web via browser (zero-install). MAUI é para apps desktop/mobile nativos.
🅰️

Angular 18Alternativa válida

Google · TypeScript obrigatório · Angular Material
    Prós
  • Fortemente tipado (TypeScript)
  • Opinativo — reduz debate de arquitetura
  • Injeção de dependência nativa (familiar ao .NET)
  • Ótimo para ERPs corporativos
  • Angular Material maduro
    Contras
  • TypeScript obrigatório (mesmo obstáculo do React)
  • Curva de aprendizado íngreme (RxJS, decoradores)
  • Mais verboso que React/Vue
Veredicto: Boa alternativa se o time aceitar aprender TypeScript. A Injeção de Dependência nativa é familiar para quem vem do .NET.
🟢

Vue.js 3Alternativa válida

Evan You · JS/TypeScript · Vuetify / PrimeVue
    Prós
  • Curva de aprendizado mais suave
  • Documentação excelente
  • Vuetify e PrimeVue são libs maduras
  • Componentes Single File (.vue) intuitivos
    Contras
  • Ainda exige JavaScript/TypeScript
  • Ecossistema menor que React
  • Sem respaldo corporativo forte (Meta/Google)
Veredicto: Opção de menor fricção se o time quiser aprender JS. Porém, não resolve o problema principal: o time é C# e não JS.

04 — Análise de Risco

E se migrarmos agora para Blazor?

O projeto já tem código produzido em React. Migrar agora tem um custo que precisa ser avaliado.

Ponto de Análise Detalhe Impacto
Código já produzido Infraestrutura OOP de CRUD (BaseCadastroConfig, hooks, 12+ componentes MUI), formulários de Entidade, Condição de Pagamento, Parâmetro e menu dinâmico precisariam ser reescritos em Razor. Alto
Esforço estimado Estimativa mínima de 2 a 4 meses de retrabalho, dependendo do escopo já migrado na data da decisão. Alto
Risco de regressão Todos os comportamentos testados manualmente (filtros, paginação, modal de edição, favoritos, menu contextual) precisariam ser revalidados. Médio
Ganho real do time O time passa a escrever C# em vez de TypeScript — ganho real de produtividade para devs sem experiência JS. Alto
Componentes UI disponíveis MudBlazor e Radzen oferecem DataGrid, Formulários, Modal e Charts. Menos opções de UI premium que o MUI, mas suficientes para um ERP. Médio
Impacto no prazo de entrega O produto entrará em produção mais tarde. As telas legadas continuarão sem equivalente web durante o período de reescrita. Alto
05 — Recomendação

Qual caminho seguir?

A recomendação depende da composição do time e da prioridade do projeto.

✅ Permaneça em React SE…

  • O time tem ou planeja contratar um especialista em JS/TypeScript
  • A prioridade é entregar o produto o mais rápido possível
  • UI premium, dashboards e animações são requisitos do produto
  • O sistema será eventualmente aberto para clientes externos (SaaS)
  • Não há plano de compartilhar modelos entre frontend e backend

🔄 Migre para Blazor WASM SE…

  • O time é 100% C# e não planeja contratar especialistas em JS
  • A manutenção de longo prazo será feita pelo mesmo time do backend
  • O produto é um ERP corporativo interno (rede controlada)
  • O bundle size inicial de 10–15 MB é aceitável (Intranet/VPN)
  • A decisão é adiada para após terminar as telas críticas em React

❌ Não recomendamos Blazor Server nem MAUI para este contexto

  • Blazor Server: dependência de conexão permanente + latência por clique = incompatível com formulários ERP
  • MAUI: não é web — requer instalação. Foge completamente do objetivo de acesso via browser (zero-install)
Nossa recomendação técnica

Continue em React agora. Valide o Blazor em paralelo.

Dado o código já produzido, a melhor estratégia é não interromper a migração atual. Em paralelo, crie um projeto Blazor WASM de prova de conceito com um formulário real (ex: Condição de Pagamento) e deixe o time usar ambos por 2–4 semanas. A decisão final deve vir da experiência prática, não apenas da teoria. Isso evita uma aposta cega e permite uma escolha embasada antes de qualquer reescrita.

06 — Plano de Ação Proposto

Próximos passos

Independentemente da decisão final, sugerimos este plano de ação para mitigar riscos.

Continuar a migração em React até concluir os formulários críticos do ERP

Priorize as telas que estão bloqueando a operação: Entidade, Condição de Pagamento, Parâmetros. O produto precisa estar funcional independentemente da decisão de stack.

Criar uma branch de prova de conceito Blazor WASM

Implemente 1 formulário real (recomendamos FCondicaoPagamento) em Blazor WASM + MudBlazor, consumindo a mesma Web API .NET 10. O time vai sentir na prática a diferença de produtividade.

Avaliação técnica com o time após 2–4 semanas de uso

Responda com dados reais: qual stack entregou mais rápido? Qual foi mais fácil de debugar? Qual a preferência do time para manutenção de longo prazo?

Tomada de decisão formal

Com base na avaliação prática, decidir se: (a) permanece em React; (b) inicia a migração para Blazor WASM após a entrega das telas críticas; (c) mantém arquitetura híbrida (API .NET + qualquer frontend).
