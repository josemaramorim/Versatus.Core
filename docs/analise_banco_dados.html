01 — Contexto e Problema

Por que sair do SQL Server?

O SQL Server e um banco de dados robusto, porem seu modelo de licenciamento e um dos mais caros do mercado — especialmente para ERPs que escalam por numero de usuarios ou por nucleo de CPU.

Agravante: SQL Server 2008 ja nao tem suporte O sistema legado roda em SQL Server 2008, cuja vida util encerrou em julho de 2019. Isso significa: sem patches de seguranca, sem correcoes de bugs e nenhuma cobertura de suporte da Microsoft. Alem do custo alto, ha risco real de seguranca e conformidade (LGPD).
i
O modelo de estrangulamento (Strangler Fig) complica a migracao No Strangler Fig, o sistema legado (WinForms + SQL Server 2008) continua funcionando em paralelo com o novo sistema (.NET 10 + novo banco). Isso significa que durante a transicao, os dois sistemas precisam coexistir — possivelmente acessando o mesmo banco de dados ou mantendo sincronismo.
02 — Estrangulamento e o Banco de Dados

Como o Strangler Fig afeta a decisao do banco?

O padrao de migracao Strangler Fig nao e simples quando ha um banco de dados compartilhado. Entender as fases e essencial para tomar a decisao correta no momento certo.

FASE ATUAL

Legado 100% Ativo

WinForms acessa diretamente o SQL Server 2008 do cliente. A nova API .NET 10 TAMBEM acessa o mesmo SQL Server 2008 (via leitura do legado). Dois sistemas, um banco.

→
PERIODO DE TRANSICAO

Coexistencia (Hibrido)

Algumas telas ja estao no novo sistema web. Outras ainda rodam no legado WinForms. Ambos precisam de dados consistentes — migracao de banco aqui e de alto risco.

→
ESTADO FINAL

Legado Desligado

Todas as telas foram migradas para web. O WinForms foi aposentado. O banco pode ser migrado para o novo SGBD sem restricoes do legado.

!
Conclusao critica: nao migre o banco durante o estrangulamento Tentar trocar o banco de dados ENQUANTO o sistema legado ainda esta ativo e de altissimo risco. O WinForms depende de features especificas do SQL Server (stored procedures legadas, tipos de dados, collation). A estrategia correta e: primeiro termine o estrangulamento, depois migre o banco.

05 — Estrategia de Migracao

Como migrar sem quebrar o legado?

A chave e respeitar o processo de estrangulamento e so migrar o banco quando o legado nao depender mais dele.

1
Seguro — Agora

Continue com SQL Server 2008 durante o estrangulamento

Enquanto o WinForms ainda esta ativo, mantenha o SQL Server 2008 intocado. A nova API .NET 10 pode ler e escrever no mesmo banco SQL Server 2008 usando o EF Core com SQL Server provider. Nao ha conflito — voce ja esta fazendo isso corretamente.

2
Seguro — Agora

Configure o novo ambiente com PostgreSQL para desenvolvimento e testes

Crie um ambiente paralelo de desenvolvimento/homologacao com PostgreSQL. Ajuste as migrations do EF Core para funcionar com Npgsql. Valide que todas as queries funcionam corretamente. Isso nao afeta o legado — e um ambiente separado.

3
Cuidado — Durante o estrangulamento

Migre stored procedures e logica de banco para a camada de aplicacao

Toda logica que esta em stored procedures do SQL Server deve ser movida para os servicos .NET (C#). Isso elimina a dependencia de features exclusivas do SQL Server e prepara o terreno para qualquer banco. Faca isso modulo a modulo, em paralelo com a migracao de telas.

4
Cuidado — Apos ultimo modulo migrado

Migre os dados do SQL Server 2008 para PostgreSQL

Quando a ultima tela do WinForms for aposentada, execute a migracao de dados. Use a ferramenta pgloader (open source, especializada em migrar de SQL Server para PostgreSQL) ou scripts ETL customizados. Mantenha o SQL Server 2008 como backup por 30-60 dias apos a migracao.

5
Destino Final

Producao 100% em PostgreSQL — SQL Server descomissionado

Com o legado aposentado e os dados migrados, o sistema web roda inteiramente em PostgreSQL. Custo de banco vai a zero (somente infraestrutura do servidor). A licenca do SQL Server pode ser encerrada ou mantida apenas para clientes que ainda nao migraram.

i
Sobre a ferramenta pgloader O pgloader (pgloader.io) e uma ferramenta open source criada especificamente para migracao de dados do SQL Server, MySQL e outros bancos para o PostgreSQL. Ele converte tipos de dados automaticamente, migra indices, constraints e dados em lote. E a ferramenta de referencia para esse tipo de migracao.
06 — Impacto no Codigo .NET

O que muda no codigo quando trocar de banco?

Com EF Core, a troca de banco e muito menos traumatica do que parece. A maioria do codigo de negocio nao muda.

Componente Impacto na troca SQL Server → PostgreSQL Nivel de Esforco
Entities e DTOs (C#) Nenhum — POCOs puras nao dependem de banco Zero
Repositorios e Servicos Nenhum se usar EF Core corretamente (sem SQL raw) Zero
DbContext e Fluent API Trocar o provider: UseSqlServer → UseNpgsql. Verificar tipos de coluna. Baixo
Migrations do EF Core Regenerar as migrations com o novo provider. Nao reescrever do zero. Baixo
Queries LINQ Nenhum — LINQ e traduzido pelo EF Core para o SQL do banco alvo Zero
SQL Raw / FromSqlRaw() Precisa revisar sintaxe (ex: TOP → LIMIT, GETDATE() → NOW()) Medio
Stored Procedures legadas Reescrever em PL/pgSQL ou mover logica para C#. Maior esforco. Alto
Funcoes de data/hora, string Algumas diferencas de comportamento (collation, case sensitivity) Medio
V
Boa noticia: o projeto Versatus ja segue as boas praticas O projeto ja usa Fluent API no EF Core (sem atributos de banco nas entidades), LINQ para queries e DTOs limpos. Isso significa que a troca de provider sera de baixissimo impacto no codigo de negocio — exatamente o cenario ideal para migracao de banco.
Nossa recomendacao tecnica

PostgreSQL e a escolha certa — mas no momento certo.

O PostgreSQL 16 e o banco de dados ideal para o Versatus Web: gratuito, maduro, com suporte nativo no EF Core, capaz de rodar on-premises ou em cloud via Docker, e preparado para multitenancy futuro (SaaS).

Porem, a migracao deve respeitar o processo de estrangulamento. A ordem correta e: (1) Continue com SQL Server durante o estrangulamento — sem tocar no banco legado. (2) Desenvolva e teste ja com PostgreSQL em ambiente de desenvolvimento. (3) Mova stored procedures para a camada C# modulo a modulo. (4) Apenas quando a ultima tela WinForms for aposentada, execute a migracao de dados com pgloader.

Para clientes que ainda nao concluiram a migracao: mantenha a instancia SQL Server deles ate a conclusao. A nova arquitetura permite rodar com SQL Server ou PostgreSQL com minima alteracao de configuracao — basta trocar a connection string e o provider do EF Core.
